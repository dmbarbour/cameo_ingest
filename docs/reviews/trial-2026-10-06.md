## Findings

### TR-001: XML names libxml2 refuses stop a model being read

> "I received many 'cannot fingerprint: Failed to parse QName ...' messages when getting started."

- **Where:**
  - the warning comes from `runner.py` (`Runner` around line 168), which catches the exception
    from `fingerprint.element_ids`;
  - `xmi.parse_into`, which reads the model for the build, uses the same `etree.iterparse`
    options.
- **Cause:** libxml2 refuses a tag or attribute name with two colons (`a:b:c`) or a trailing colon
  (`a:`), and lxml raises `XMLSyntaxError: Failed to parse QName 'a:b:c'`. Both parsers fail alike
  (reproduced), so the projects that couldn't be fingerprinted almost certainly failed to build
  too. The fingerprint warning is just the first sign. A profile or stereotype whose name holds a
  colon would produce such names, but that is a guess until we see an example.
- **What recovery does:** with `recover=True`, lxml keeps every element, its `xmi:id` and its
  attributes. A name it can't split stays a literal string, such as the tag `'a:b:c'` (tested).
- **Remediation:**
  - **TR-001R1:** both parsers read with `recover=True`. Each entry that needed recovery gets one
    warning that counts the recovered errors and quotes the first. Such an entry is never silently
    accepted.
  - **TR-001R2:** the parser's handling of literal names. A stereotype application with an
    unsplittable tag must still be found by its `base_*` reference, or else be reported. Check
    that `semantics` doesn't misread it.
  - **TR-001R3:** a synthetic fixture with such names (a tag, an attribute, a trailing colon),
    built, with the invariants checked; `status` reports the recovered entries.
  - **TR-001R4:** ask the maintainer for one full message, or the profile it names, to confirm the
    cause.
- **Done (0.21.2):**
  - **R1:** `xmi.read_events`, used by `parse_into` and `fingerprint.element_ids`, reads with
    `recover=True`. It keeps the namespace faults (libxml2's `NAMESPACE` domain) in
    `ModelIndex.recovered`, and raises `ModelReadError` ("damaged XML in ENTRY, line N: …") for
    any other fault once the entry is read. The fingerprint no longer fails, and the build warns
    once per entry.
  - **R2:** `qname` splits a literal `prefix:rest` tag at its first colon, so
    `<sysml:Block:Mark base_Class=…>` is a stereotype application named `sysml:Block:Mark` on its
    base element.
  - **R3:** `tests/test_xmi.py::test_names_namespaces_cant_split` covers a two-colon tag, a
    two-colon attribute and a trailing colon, with the invariants checked, the README's "Read with
    recovery" line and `status`'s "read with recovery" line; a truncated entry still fails. On the
    samples, recovery reads the same elements and stereotypes, needs no recovery, and takes the same
    time (7.2 s against 7.4 s).
  - **R4 (0.21.3):** the maintainer's message: "Failed to parse QName
    'xmlns:MD_Customization_for_SysML::additional_stereotypes', line 2". It is a namespace
    declaration on the root, with a prefix that is the qualified name of a package inside a
    profile (`MD Customization for SysML`), so every application of its stereotypes is refused too.
    R2 split a literal tag at its first colon, which reads such a stereotype as
    `:additional_stereotypes:Name`. Now a literal tag splits at its last colon (a local name never
    holds one), `StereotypeApplication.name` likewise, and the refused declaration, which recovery
    keeps as a root attribute, gives the application its profile's URI. The test has this case.

### TR-002: browsing by subject

> "It would be convenient if the search page is a bit more browseable, e.g. by subjects."

- **Now:** the page has only a query box, a model filter and a type filter
  (`assets/search.html`, line 36). With no words typed, it shows nothing to browse.
- **What "subjects" could be built from:**
  - **(a) the package tree:** each model's packages, nested, with their counts. Deterministic;
  - **(b) kinds:** requirements, blocks, activities and so on, as the type filter has them, but
    listed with counts;
  - **(c) what things are for:** the `about_class` that the about requests give each package and
    diagram (ADR-0029). Generated text, so labelled;
  - **(d) the identifier index:** requirement-id families and threads (`CROSSREF.md`).
- **The maintainer's answer to Q1** (2026-10-06): none of these alone. Searches already return
  hundreds of diagrams for one subject. What's wanted is discovery of diverse things, "the
  opposite of 'closest match' searches, i.e. building a list of mostly-independent cliques". The
  maintainer suggests that an AI propose a few viable splits, and that a small panel of AI judges
  measure them during development, while the maintainer checks in real trials.
- **Remediation:** TR-002R1, plan SB (`docs/plans/subjects-2026-10-06.md`): splits of each model
  into subjects (by package, by shared elements, by words, and proposed by the LLM), judged by a
  panel. The best one serves browsing, results grouped by subject, and a diverse first page.
- **Done (0.22.0):** ADR-0031; the search page's browse pane and results grouped by subject, the
  workbook's Subjects sheet. Open until the maintainer's trial.

### TR-003: choosing models

> "instead of all-or-one when selecting which files to search, we can get a dropdown with each
> model and checkboxes or similar. We need more than model name when selecting, e.g. also the
> dates and filepaths, and perhaps also the analysis on related files."

- **Now** (corrected 2026-10-07, after the maintainer: "I cannot actually see much in the HTML
  dropdown list to guide selection, just the model name and a bit of the ID, not any of the other
  metadata"):
  - **What a reader sees:** one dropdown, "All models" or a single model. Each entry is the
    project's label, the start of its file name and a short id (`Riverbend_Water_Treatment_Works
    [d1fa7680]`), and nothing else: no date, no path, no Cameo version, no sign that two entries
    are versions of one model. Files of the same name differ only by the id.
  - **What the page holds but shows only on an opened item:** each project's paths and `--meta`
    values (the item's Source and Metadata lines) and its counts (`searchpage.py`, around line
    121). The dropdown uses none of it.
  - **What the page doesn't hold:** the save time and the version groups (`cameo-ingest projects`
    and `groups`, ADR-0020), which are in `state.sqlite` only, and the Cameo version, which is in
    the catalog but not passed to the page.
  - **Since 0.22.0,** the browse pane lists models by family, with their diagram and version
    counts, but still no dates or paths.
  - **The workbook's Projects sheet** has each project's paths (Source), metadata, Cameo version
    ("Saved by") and counts, but no save time and no group.
- **Remediation:**
  - **TR-003R1:** the export puts in each project's block its save time, Cameo version, every
    path, and its version group (newest first, and whether it is the newest).
  - **TR-003R2:** a model chooser with a checkbox per model, showing name, save time, version and
    paths:
    - "All", "None", and "newest of each group" as shortcuts;
    - a text filter over names and paths;
    - the choice shown as "3 of 27 models".
  - **TR-003R3:** the same facts in the workbook's Projects sheet: add the save time and the
    group.
  - **Plan LN** (`docs/plans/lineage-2026-10-07.md`) carries these out, and adds lineage. The
    maintainer: "it's reasonably difficult to distinguish versioned models vs. rival models with a
    shared root". Element ids carry their maker and creation time, which tells a later version
    (the same makers, later) from rivals on a shared root (other makers, the same period).
  - **Done (0.24.0):** the model chooser, each model's facts and lineage in the page and the
    workbook, and families from lineage (ADR-0032). Open until the maintainer's trial.

### TR-004: shared provenance for shared requirements

> "It would be convenient if shared requirements had shared provenance."

- **Now:** a requirement found in several models is a separate item in each, and each shows only
  its own model's provenance. Two models can share one in two ways:
  - **the same element** (the same `xmi:id`): versions of a model, or a used project;
  - **the same requirement id** in different elements (`CROSSREF.md`, the workbook's Identifiers
    sheet).
- **Remediation:** TR-004R1, after Q2. One reading: a requirement's view lists "Also in", meaning
  every model and file holding the same element or id, each a link. Search results could also
  fold such copies into one row, with a count.

### TR-005: links at the `[n]` tags in a diagram's text

> "The links in the SVG diagrams are great! But it would be nice to also support links in the
> text descriptions below, e.g. at each [1] or [2] or [3] the number could be hyperlinked when
> possible."

- **Now:**
  - each shape in the SVG carries its element's key (`data-k`), and a click opens the element
    (`search.js`, around line 527);
  - the diagram's text and descriptions refer to shapes by the same number tags;
  - the page has no map from tag to element, except inside the SVG, which is absent when the page
    has no sketches (`--sketches none`, the default).
- **Remediation:**
  - **TR-005R1:** the catalog's diagram record carries `tags`, from number to element key, for
    the diagram and each module (which number their shapes on their own, if they do; check).
  - **TR-005R2:** in the diagram's text, its generated descriptions and its chunk text, a `[n]`
    whose number is in the map becomes a link to the element. Text stays `textContent`: the link
    is built as a node, never as HTML.
  - **TR-005R3:** a Node test, including a module's own numbering and a `[n]` with no shape.

### TR-006: "As the RAG reads it"

> "We might rename 'As seen by RAG' since it's a bit less literal."

- **Where:** `search.js`, line 506: the heading of the item's chunk text (`it.c`).
- **Remediation:** TR-006R1, a heading that says what it is, for example "Indexed text (the chunk
  given to search tools)". The maintainer picks the wording (Q3).

### TR-007: the workbook's Find sheet

> "Excel workbook: find page should have a search button and, if feasible, some indicator that
> it has started and of progress."

- **Now:** the words go in B2:D2. One dynamic-array `SORTBY(FILTER(…))` over the Search sheet
  recomputes whenever a cell changes (`workbook.py`, around lines 182 to 211). Excel shows no
  sign of work but its own status bar ("Calculating: n%"), and a large workbook stalls on each
  keystroke's change.
- **What is feasible:**
  - a real button needs a macro (`.xlsm`). Macros are often blocked, don't run in Excel for the
    web, and an `.xlsm` from a tool is a security flag;
  - Office Scripts buttons need a script stored in the user's OneDrive;
  - without either, we can only:
    - **(a) a "Search" cell that starts it:** the formula computes only when a cell such as `F2`
      reads `go` (or a checkbox, in Excel versions that have them), so typing words costs
      nothing, and the search runs once;
    - **(b) a status cell beside the results:** "Searching…" can't show during a calculation,
      since Excel doesn't redraw, but "Searched 74,407 rows: 312 matches" can show after it;
    - **(c) a cheaper formula:** `LET`, one pre-lowered text column, and the first word tested
      first;
    - **(d) the About sheet** naming the status bar's indicator.
- **Remediation:** TR-007R1 to R3, as (a), (b) and (c); then a timing on the samples and on a
  workbook of the maintainer's size, in Excel itself (our LibreOffice lacks `FILTER`).

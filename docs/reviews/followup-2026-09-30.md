## Findings

### FU-001: Every directed diagram edge is listed and drawn in reverse

**Severity:** High · **Verified:** Reproduced · **Where:** `src/cameo_ingest/diagrams.py` (`edges`, `describe`, `render_png`)

A diagram's connection list takes each edge's direction from the order of the drawn path's
ends (`linkFirstEndID`, `linkSecondEndID`). Cameo stores the target as the first end, so every
directed edge reads backwards. Those edges include control and object flows, dependencies,
«satisfy», «deriveReqt», generalizations, «include» and transitions. The sketch's arrowheads
are drawn at the wrong end for the same reason.

These lists appear on every diagram page, and the LLM prompt presents them as the
authoritative description of the diagram. The model then either repeats a reversed direction
or quietly overrides it, and neither outcome can be trusted. `relationships.csv`, the element
sections and the ledgers take their directions from the model and are correct.

**Evidence:**
- Across every drawn edge that shows a model relationship, the drawn direction is the reverse
  of the model's source and target:

  | Sample | Reversed edges |
  |---|---|
  | Package_Delivery_Drone | all of them: 41 Abstraction, 34 ControlFlow, 53 ObjectFlow, 2 Include |
  | TMT | all but one of 5,554 (the exception is a single Transition): 3,309 ControlFlow, 918 ObjectFlow, 392 Generalization, 339 Dependency, 241 Transition, 182 InterfaceRealization, 126 Usage, 22 Include, 22 Abstraction, 2 InformationFlow |

- **Example:** the drone's use-case page lists `Monitor Power →[Include]→ Deliver Package`,
  but the model's `<include>` elements are owned by Deliver Package, with Monitor Power as the
  `addition`.

**Remediation:**
- **FU-001R1:** When an edge shows a model relationship, orient it by the relationship's source
  and target. Otherwise, take `linkSecondEndID` as the source, which matches every measured
  case.
- **FU-001R2:** Draw the arrowhead at the target end of the path.
- **FU-001R3:** Add a fixture layout that stores an «include» and a «satisfy» edge in Cameo's
  order. Add an invariant for every sample run: each directed edge with a relationship is
  listed as source → target, as in `relationships.csv`.

### FU-002: Item flows on connectors are missing from diagram text

**Severity:** High · **Verified:** Reproduced · **Where:** `src/cameo_ingest/diagrams.py:describe`, `src/cameo_ingest/semantics.py`

In internal block diagrams, what each connector carries is modelled as an «ItemFlow» (an
InformationFlow with `realizingConnector` pointing at the connector and `conveyed` pointing at
the items). The connection list names only the connector itself, so the most informative part
of the diagram ("Energy", "Throttle Control Signal", "Drone Arrival Alert", "Forces") is
missing. Pairs of parts joined by two connectors show up as identical duplicate lines. The
labels are visible in the sketch, but the model, told that the list is authoritative, left
them out.

**Evidence:**
- **Diagram page:** the drone's `Drone` diagram lists 18 bare `—[Connector]—` lines, while its
  sketch shows about 20 item-flow labels.
- **The model:** it has 82 `realizingConnector` references and 91 «ItemFlow» stereotype
  applications.

**Remediation:**
- **FU-002R1:** Index information flows by `realizingConnector` (and by `realization`, for
  flows realized by associations). Show their conveyed items on the connector edge, for
  example `—[Connector: Energy; Charging Complete Alert]—`, both in the diagram page and in
  the prompt.
- **FU-002R2:** Check where item flows appear in the sections of the parts and blocks at each
  end, and list them under the owning block where they don't. Parts are members, not
  sections, so today these flows may not appear anywhere readable.
- **FU-002R3:** Add a fixture connector realized by an item flow, and assert that the diagram
  page shows the conveyed items.

### FU-003: Diagram labels: unnamed pins read `: Type`, and sketches cut off types and show «DiagramInfo»

**Severity:** Low · **Verified:** Reproduced · **Where:** `src/cameo_ingest/diagrams.py` (`element_label`, `render_png`)

- **Unnamed pins and parts:** these are labelled with an empty name followed by the type, as
  in `: Low Battery Alert →[ObjectFlow]→ Monitor Power.output : Low Battery Alert` in the
  activity diagram.
- **Cut-off labels:** sketch labels wrap to at most three lines, and the stereotype comes
  first, so the type is what gets cut off (`«PartProperty» communication Subsystem :`).
- **The frame's stereotype:** a diagram frame shows `«DiagramInfo»` as if it were a
  stereotype, because it now is one (BASE-001).

All three make both the page and the prompt harder to read.

**Remediation:**
- **FU-003R1:** Label an unnamed typed element by its type alone, without the leading colon.
- **FU-003R2:** Leave `DiagramInfo` out of the stereotypes shown on diagram frames.
- **FU-003R3:** When a sketch box is small, keep the name and type in preference to the
  stereotype.

### FU-004: Diagram descriptions invent groupings and use Markdown formatting

**Severity:** Medium · **Verified:** Reproduced · **Where:** `src/cameo_ingest/pipeline.py` (`DIAGRAM_PROMPT`)

- **Invented grouping:** the activity diagram's description says its actions are "categorized
  by function" and names four groups ("Power & Maintenance", "Logistics"...). The diagram has
  no such grouping, so this structure is presented as the model's own content when it isn't.
- **Formatting:** it uses bold pseudo-headings, bullet lists and backticked names. The summary
  prompt asks for plain prose, and the diagram prompt doesn't. Markup is noise in chunk text,
  and it makes descriptions inconsistent with each other.

**Remediation:**
- **FU-004R1:** Revise `DIAGRAM_PROMPT`:
  - ask for plain prose, with no headings, bold text or code formatting;
  - group or categorize only what the diagram itself groups (frames, partitions, nesting);
  - explain the connection notation (source → target, with the relationship kind and any
    conveyed items in brackets).
- **FU-004R2:** Compare the same items before and after the change, with the tooling of the
  quality plan (FU-006).

### FU-005: Package summaries see only the first 12,000 characters of a package

**Severity:** Low · **Verified:** Reproduced · **Where:** `src/cameo_ingest/pipeline.py` (`SUMMARY_INPUT_CHARS`)

Four of the drone's five packages were cut: from 49,869, 47,159, 39,978 and 12,715
characters to 12,000. Every element name still reaches the model, because a package's own
section lists its members first. What gets cut is the documentation, relationships and tagged
values of later elements. The summaries checked were accurate and useful anyway, so this is a
limit on depth, not a source of errors.

**Remediation:**
- **FU-005R1 (decision needed):** Choose one:
  - (a) give the summary a compact input that fits whole packages: the package's ledger rows,
    plus each element's first documentation sentence and its relationships;
  - (b) summarize large packages in parts, then combine the parts.

  Compare the options with the quality tooling before choosing.

### FU-006: LLM output quality is not measured

**Severity:** Medium · **Verified:** By inspection · **Where:** `src/cameo_ingest/llm.py`, tests

Nothing samples, rates or tracks the quality of generated text. The tests check only its
mechanics: labelling, caching, replay. Spot check 1 needed an ad hoc run and hand-picked
items, and it can't be repeated as-is. The LLM store deliberately keeps no prompts, so the
exact input behind a response has to be rebuilt by hand.

**Remediation:**
- **FU-006R1:** Carry out `docs/plans/llm-quality-2026-09-30.md`:
  - reproducible spot-check sets that both the maintainer and Claude can rate, covering both
    the responses and the prompt templates, shown with stand-ins for their image and text
    slots;
  - a panel of independent model judges;
  - a report comparing raters, used to measure fixes such as FU-001, FU-002, FU-004 and
    FU-005 before and after.
